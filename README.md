# Mad Mallard Platform

Portable, open-source Docker Compose deployment for a shared business application platform.

## Planned applications
- Matomo — web analytics
- Umami — privacy-focused website analytics
- Supabase — backend platform
- Metabase — business intelligence
- Chatwoot — customer support
- n8n — workflow automation
- Horilla — HR management
- Authentik — identity and access management
- Homepage — application portal

## Design requirements
- One primary `compose.yaml` and an `.env.example`.
- Reuse database engines, Redis and infrastructure only where upstream software supports it; isolate databases, accounts and data.
- Preserve vendor-supported Supabase services and dependencies.
- Support deployment to any compatible Docker Compose host without fixed host IPs.
- Integrate with an existing Traefik, monitoring and backup stack without duplicating those services.
- Provide optional standalone deployment prerequisites and clear configuration.
- Support shared branding and SSO where upstream applications allow it; document limitations.
- Use supported, pinned container versions; never commit secrets.
- Include validation, tests, security checks, backup/restore instructions and operational runbooks.

> Status: Initial repository setup. The complete stack is not yet implemented or deployable.

## Umami analytics

Umami runs on the existing PostgreSQL service, using a separate `umami` database and login. Configure `UMAMI_DB_PASSWORD` and `UMAMI_APP_SECRET` in your local `.env` (use a URL-safe database password). The UI is available at `http://localhost:3005` by default; change `UMAMI_PORT` if necessary.

**One-time database provisioning:** the PostgreSQL volume is already initialized on existing installations, so scripts in `init/postgres` will not run again. Create the isolated role and database before starting Umami. In a PostgreSQL superuser session, run `CREATE ROLE umami LOGIN PASSWORD '<your-UMAMI_DB_PASSWORD>';` and `CREATE DATABASE umami OWNER umami;` (substitute your secret locally, never commit it). If the role/database already exists, reuse it instead of recreating it.

Start with `docker compose up -d umami`, check `docker compose ps umami`, and visit `http://localhost:3005`. Change Umami's default admin password immediately. To collect website metrics, add the per-website tracking script generated by Umami to each site's pages; creating a website or map alone does not collect traffic. The script must be reachable from visitors' browsers over HTTPS in a production deployment—`localhost` works only for local testing. For active testing against `drakeg/umami`, use the fork-sync process below instead of the upstream image.

### Keep the Umami fork current

The `Sync Umami fork image` GitHub Actions workflow runs on every push to this platform's `main`, on published releases, on a weekly schedule, and on manual dispatch. It checks out the latest `drakeg/umami` `master` commit, builds its Dockerfile, and publishes `ghcr.io/drakeg/madmallard-umami:edge` plus a commit-specific image tag. A failed build will not publish an updated image. The GitHub package must be readable by the deployment host; private packages require registry authentication.

**For local full testing:** run `bash scripts/sync-umami-fork.sh` on the Compose host. This fetches the latest fork commit, builds a commit-tagged image, updates only the local `UMAMI_IMAGE` setting, and recreates only the Umami container. It checks the health endpoint and rolls back to the previous image on failure. The PostgreSQL data and credentials remain unchanged. The script needs Docker, Git, Python 3 and curl. It leaves a `.env.umami-backup` file if deployment fails; keep it private.

Publishing the image in GitHub Actions **does not automatically redeploy a private Mac or other host**. Run the local sync script after a new build, or configure an authorized deployment runner. The weekly Umami Image Sync task separately reviews the latest build and deployment status.
